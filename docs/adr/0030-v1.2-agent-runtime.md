# ADR-0030 — v1.2.0: Agent background runtime (`frtrol agentd`)

- Status: ACCEPTED (owner instruction 2026-10-03: master prompt §17 — "agent
  should not require a terminal to stay open… this is a hard requirement";
  approved via "lanjut ke ADR dan jalankan mission project 1.2.0")
- Date: 2026-10-03
- Research: docs/research/r8-agent-runtime-reconnect-ux.md, r11-realtime-sse-polling.md
- Depends on: ADR-0028, ADR-0029

## Context

v1.1's agent CLI is a one-shot process: every command opens a fresh HTTPS
request; credentials live in files; nothing runs in the background. The master
prompt requires: connect, close the terminal, the runtime keeps the logical
connection alive (reconnect, network changes, session-state reporting, clean
shutdown, revocation/expiry reaction) — and "must not become an uncontrolled
permanent backdoor" (§18).

## Designs considered

1. **OS service** (systemd `--user` unit / launchd / Windows service). Rejected
   as default: needs per-OS packaging + root/session-bus cooperation, breaks in
   containers/SSH/CI, and the daemon-side model is already self-hosted
   single-user. (Documented as an optional deployment: the runtime is just an
   executable, an operator may supervise it with any service manager.)
2. **Foreground daemon the operator nohups/tmuxes.** Rejected: the prompt
   demands the *default* experience work with zero operator ceremony (§17).
3. **Supervised detached child spawned at connect** (chosen).

## Decision

`frtrol agent` performs the login flow, stores `connection.json` (0600) in the
agent home (`FARCONTROL_AGENT_HOME`, default `~/.farcontrol-agent`), then
spawns **one** detached runtime — `frtrol agentd` (hidden subcommand):

- **Detach**: own process group (`process_group(0)`), stdio → `agentd.log`,
  survives the parent terminal's SIGHUP; CLI exits immediately after spawn.
- **Single instance** per agent home: pidfile with liveness check (stale pid is
  reclaimed).
- **Heartbeat**: HMAC-signed `GET /v1/heartbeat` every 15 s (1 s in
  FARCONTROL_TEST_MODE). The daemon keeps an in-memory agent map
  (name → last_seen, connected_at) → owner console/CLI show live agent state
  (master prompt §32). First sighting audits `agent.seen`; going silent >45 s
  sweeps to `stale` and audits `agent.timeout` once.
- **Reconnect**: network errors → state `reconnecting`, exponential backoff
  1→2→4… capped 60 s with ±20% jitter (r8). Retries forever — a temporary
  network failure must not destroy the logical session (§20).
- **Terminal states** (fail closed, credentials erased, clean exit):
  `expired` (401 auth_failed — the daemon session that minted this key is
  gone), `revoked`/`device_locked`, operator `stop`. A 401 is definitive: the
  key was rotated at the new start (ADR-0028); retrying it would only hammer
  the backoff engine.
- **Operations do not proxy through the runtime.** `exec`/`term`/file commands
  call the daemon directly from the CLI using the shared `connection.json` —
  one fewer hop, lower PTY latency (§22), and the runtime stays small. The
  runtime owns *liveness/state*, not the data plane.
- `frtrol agent status [--json]`: reads the runtime's `status.json` + pid
  liveness (no network dependency). `frtrol agent stop`: SIGTERM → clean
  shutdown → credentials cleared.

## Consequences

- The §50 DoD is testable end-to-end: spawn `frtrol agent`, exit, assert the
  agentd pid is still alive and heartbeating; kill the daemon, watch the state
  machine reach `expired` with credentials gone.
- Idle cost: one HTTPS request / 15 s — negligible vs the prompt's §44 budget.
- The runtime never holds more privilege than the credential file it guards;
  erasing credentials on terminal states is the anti-backdoor rule.
