# ADR-0023 — v0.9.0: OS keyring, progressive auth backoff, startup config validation

- Status: ACCEPTED (owner instruction 2026-10-02: "selesaikan project farcontrol sampai versi 1.0.0")
- Date: 2026-10-02
- Supersedes: none (extends ADR-0005 §backoff, ADR-0008, ADR-0016, D-023)

## Context

v0.8 closed the agent-identity surface (ADR-0022). Three honest gaps remain open in
`tracking/PROGRESS.md` before a 1.0.0 release can claim production readiness:

1. **ID-04** — the device secret lives on disk (SQLite meta + file 0600, deviation D-023).
   The spec asks for the OS secret store.
2. **SC-01 / §97-3** — auth failures get a *flat* sliding-window lockout (10 fails/60 s → 429).
   After the window slides, an attacker resumes at the same rate forever. The spec asks for
   *progressive* backoff.
3. **SC-02** — config errors are discovered lazily (at first use) or silently ignored
   (wrong-typed `[policy]` values are skipped by `Policy::from_config`). The spec asks for
   config validation **at startup**, fail-fast.

## Decision

### 1. OS keyring — opt-in `[identity] secret_store = "keyring"` (default "file")

- Backend = **Linux kernel keyring (keyutils)**, spoken via raw `add_key(2)`/`keyctl(2)`
  syscalls through `libc` — no new crate, no D-Bus, no keyutils userspace tools required.
- Key material: persistent user keyring (`KEYCTL_GET_PERSISTENT`), key type `user`,
  description `farcontrol-agent-<sha256(data_dir)[0..16]>` — one key per data dir, so
  multiple daemons/users do not collide.
- In keyring mode the agent token is **never written to disk**: no `agent-token` file, no
  `agent_token` meta row in SQLite. The daemon reads it from the kernel **per request**
  (same read-per-request discipline as file mode → rotation stays instant).
- Mode is chosen at `init` time via `config.toml`; switching modes after init fails closed
  with an explicit error (no silent fallback between stores).
- `rotate` updates the key in place (`add_key` on an existing type+description updates the
  payload). `panic` rotates the same way.
- **Backup** materializes the token into the archive (the archive already contains every
  secret by design, mode 0600): the daemon writes a 0600 `agent-token` file into the data
  dir for the duration of the `tar` and unlinks it immediately after. **Restore** reads the
  extracted file, writes the secret back into the kernel keyring, and removes the plaintext
  file — the restored dir converges to the archive's own configured mode.
- `doctor` gains a `secret_store` check: keyring readable + no stray plaintext file.
- Non-x86_64 Linux and non-Linux targets: keyring mode refuses to start (fail closed);
  file mode is unaffected. Kernel keyring unavailable in the environment → init fails with
  a clear error; the owner falls back to `secret_store = "file"`.
- Why not Secret Service/D-Bus: adds a heavyweight dependency chain and a user session
  dependency for a daemon; the kernel keyring is always present, permission-checked by the
  kernel, and survives restarts. Documented as the Linux answer to ID-04 (deviation note
  kept: this is the *self-hosted Linux* answer, not a cross-OS keychain story).

### 2. Progressive auth backoff (SC-01)

Two layers, both fail closed, both single-tenant-global (extends D-034):

- **Burst window (unchanged)**: ≤10 failed auths / 60 s → 429 `rate_limited`.
- **Progressive lockout (new)**: a *strike counter* counts consecutive failures.
  At strike ≥ 10 the box locks for `60 s × 2^(strikes−10)`, capped at 3600 s.
  **Every attempt while locked extends the lock** (hammering makes it worse, never better).
  A **successful** HMAC authentication resets strikes and clears the lock (owner/agent
  recovery). Test mode: 6 strikes, 2 s base, 8 s cap.
- Lock state is in-memory (restart clears it — same as the burst window; documented).
- Audited as `auth.backoff` **only when the lock duration changes** (bounded audit growth:
  an attacker hammering at cap produces no new rows).
- Applies to the **agent plane** and **web-UI login**. The admin plane (`verify_admin`)
  stays deliberately unlocked — the owner's approve/revoke/panic path must remain usable
  *during* an attack (§97-14). This is the pre-existing v0.2 design; we keep it explicit.
- `farcontrol_auth_lockout` / `farcontrol_auth_strikes` metrics added.

### 3. Startup config validation (SC-02)

`Config::validate()` runs in `init` and `run()` **before any listener binds or state
opens**. Rejected (fail fast, exit code 2, message prefixed `config_invalid:`):

- binds that are not valid `host:port`, port 0, admin bind not loopback;
- empty `home_root`;
- `secret_store` not in {`file`, `keyring`};
- recognized `[policy]` keys with wrong TOML types or out-of-range values
  (≤0 hours/ttl/timeouts/caps, `max < min`, non-string denylist entries);
- `[audit] max_events` negative or non-integer.

Unrecognized keys stay ignored (forward compatibility, unchanged). `doctor`'s config
check is upgraded from "parses" to "parses **and** validates".

## Consequences

- (+) ID-04 closes for Linux: the credential never touches disk in keyring mode.
- (+) Brute force becomes exponentially expensive; recovery stays one successful auth away.
- (+) Config mistakes surface at startup with a stable exit code instead of at 2 a.m.
- (−) keyring mode couples the credential lifetime to the user's persistent keyring:
  wiping the keyring (`keyctl clear`) invalidates the agent identity → re-init required.
  Documented in README + doctor.
- (−) Backup still exports the secret (by design — it is the disaster-recovery artifact).
- (−) The escalation math must be mutation-checked like every security control: M1
  (escalation disabled), M2 (validation removed), M3 (keyring writes plaintext anyway).
