# ADR-0024 — v1.0.0: release engineering and the honest final sweep

- Status: ACCEPTED (owner instruction 2026-10-02: "selesaikan project farcontrol sampai
  versi 1.0.0", "releasenya itu cuman versi 1.0.0", "readme md nya sangat amat humanize
  profesional nice", "reponya … isinya wajib lengkap banget")
- Date: 2026-10-02
- Related: D-042 (owner override of the spec's v0.1 ceiling), ADR-0020 (supply chain),
  ADR-0023 (v0.9 hardening)

## Context

v0.9.0 closed the last code-level gaps that mattered (ID-04 keyring, SC-01 progressive
backoff, SC-02 config validation). What stands between "0.9.0 verified" and a **1.0.0
release** is not more features — it is:

1. one more honest verification pass (panic **under stress**, §97-14, the last TODO row
   that has real substance);
2. closing the "assurance" requirement rows (SC-03/04/06, §97-14, ID-08) **by
   verification**, not by writing new code — they are absence/property claims and the
   evidence already exists;
3. release engineering: humanized README, LICENSE, CHANGELOG, SECURITY.md, CONTRIBUTING
   guide, CI workflow, GPG-signed artifacts (SC-07 "signed releases" PARTIAL → signed);
4. exactly **one** GitHub release (v1.0.0) on a complete repo — per explicit owner
   instruction, no intermediate 0.x releases are published.

## Decision

1. **Code delta in 1.0.0 is deliberately tiny**: version bump + e2e §32
   (emergency stop while terminals and commands are in flight: every terminal killed,
   session revoked, in-flight commands bounded by their timeouts, old token dead, new
   cycle works, daemon healthy). Everything else is verification + docs + packaging.
   A 1.0.0 that adds features at the same time it declares stability would be lying
   about at least one of the two.
2. **Assurance rows closed by evidence**:
   - SC-03 (no hidden persistence/covert startup/harvesting): fixed endpoint set, no
     autostart beyond the documented systemd unit, secret-scan CLEAN.
   - SC-04 (no secrets in source/logs, no debug endpoints, no wildcard CORS): secret-scan
     + audit canary (EVIDENCE-001 §8) + endpoint list is a compile-time router.
   - SC-06 (privacy, metadata-only): audit rows carry ids/bytes/durations only.
   - §97-14: e2e §32 (stress panic).
   - ID-08: schema v3 unchanged 0.8→1.0, migrations table, e2e §22 restore.
   - ID-05 stays PARTIAL-by-design (self-hosted HMAC needs the key itself; keyring mode
     keeps it out of DB+files entirely; verifier-only storage remains a hosted-CP
     concept — D-023).
3. **Docs** (repo-complete): humanized README (the product story, quickstart, security
   model, verification story, honest limitations), MIT LICENSE, CHANGELOG (0.1→1.0),
   SECURITY.md (supported version = 1.0.x, reporting), CONTRIBUTING.md (how to run the
   full verification wall before a PR), `.github/workflows/ci.yml` (clippy -D warnings,
   unit tests, e2e on ubuntu-latest — where the kernel keyring is real, so §31 runs its
   full path).
4. **Packaging**: release binary, `.deb` (systemd hardening), source zip, SPDX SBOM,
   SHA256SUMS, and a **GPG detached signature** of SHA256SUMS; the signing public key +
   fingerprint ship in the repo; checksums + signature are release assets.
5. **GitHub**: single push of the complete tree (code, docs, ADRs, tracking, evidence,
   reports, spec), one tag `v1.0.0`, one release with assets and release notes.
   Intermediate versions exist only in CHANGELOG + tracking, exactly as the owner
   instructed.

## Consequences

- (+) 1.0.0 means what it says: every claim in it is either machine-verified in this
  repo's CI or explicitly listed in "Limitations".
- (+) The release is signed and checksummed (SC-07 fully closed).
- (−) The GPG signing key is generated at release time; the owner should re-sign future
  releases with their own key (documented in SECURITY.md).
- (−) CI e2e runs on GitHub runners (real kernels); the sandbox where this was authored
  cannot exercise the keyring happy path (ADR-0023 §probe) — the CI workflow is where
  that path becomes continuously verified.
