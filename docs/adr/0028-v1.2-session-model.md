# ADR-0028 — v1.2.0: Ephemeral session credentials (the v1.2 session model)

- Status: ACCEPTED (owner instruction 2026-10-03: v1.2.0 master engineering prompt
  §1–§10, §19 — "the session should be ephemeral… when the FARcontrol session
  ends, its session credentials must no longer provide access"; chat: "lanjut ke
  ADR dan jalankan mission project 1.2.0")
- Date: 2026-10-03
- Research: docs/research/r7-pairing-ephemeral-credentials.md, r13-session-time-ux.md
- Supersedes: ADR-0025 §1–§3, §5–§6 (multi-device registry with permanent
  passwords) — v1.1 installs are migrated, not preserved (see §5 below)

## Context

v1.1 requires `frtrol device add` before anything works, and the device password
is **permanent** until manually rotated. The master prompt judges this wrong for
the product's story: `frtrol start` alone must produce a complete, ephemeral
credential set — and every credential it produced must die when that daemon run
ends. The core distinction becomes:

- **Device identity** — stable `FAR-XXXX-XXXX` id for this machine (created at
  init, never changes). An identifier, never a secret (§4 of the prompt).
- **Session access** — credentials minted per `frtrol start`, invalid after it.

Non-negotiable kept: authentication ≠ authorization. The session password only
authenticates; every access still requires an owner-approved grant (5–72 h,
scoped, revocable). No change to invariant #1.

## Designs considered

1. **TTL-bound session credentials** (password valid N hours, checked against a
   deadline even mid-run). Rejected: introduces an artificial duration limit the
   owner prompt explicitly forbids (§16: "no artificial connection duration
   limit"), and a timer adds a race surface for zero UX benefit.
2. **Per-start rotation** (chosen). The daemon run itself IS the session. New
   password + new HMAC key + new admin token at every `frtrol start`; old ones
   are dead because verification state lives in the daemon process. No timers,
   no expiry races, no cleanup jobs. Fail-closed by construction: a dead daemon
   cannot authenticate anything.

## Decision

### 1. What `frtrol start` mints (all rotated every start)

| Credential | Consumer | Storage |
|---|---|---|
| Session Password | agent login | Argon2id hash in the machine device row (shown once at start) |
| Session Key | HMAC proof-of-possession after login | machine device row (file mode) / keyring payload (keyring mode) |
| Admin Token | web console + owner CLI | meta + `admin-token` file 0600 (shown once at start) |
| Session ID | identifies this daemon run (reconnect detection) | in-memory only |

`frtrol rotate` re-mints password + admin token mid-run (credential hygiene);
`frtrol panic` additionally revokes every grant, kills terminals, clears agent
state. Login does **not** rotate the session key (unlike v1.1) — several agents
may hold it concurrently; the master prompt's §42 concurrency model is "one
shared session credential = one principal", like a Wi-Fi password. Per-agent
attribution stays at the audit layer via the declared agent_name (existing,
labeled "declared — not verified").

### 2. Machine device (single-device model)

The v1.1 registry (many devices, permanent passwords) is replaced by exactly
one row: the machine itself (`id` = the stable device id from meta, `name` =
"machine"). Its `password_hash` = current session password; its `device_key` =
current session key. The entire v1.1 login/backoff/lock machinery is reused
unchanged against this row. `X-Far-Device` on requests must carry the machine
id; anything else fails auth generically (no existence oracle, S11).

### 3. Session end semantics (master prompt §19, §36)

- Daemon exit (Ctrl-C, crash, `frtrol stop`): in-memory session dies. Approved
  grants **persist** (they are time-bounded policy objects, not credentials) but
  are unusable until the next start mints a new session key — the agent must
  re-login with the new session password. Temporary failure does not destroy
  logical sessions (§20); stolen old credentials never silently regain access
  (§6) because the new start rotated them.
- `frtrol panic`: revokes every grant + rotates everything (existing behavior).

## Consequences

- Agent handover = Device ID + Session Password, both printed by `frtrol start`
  once (never re-printed; r7). Old-password and old-key rejection after restart
  are e2e-tested.
- The banner/`status` never show the password again; `frtrol rotate` shows the
  new one once.
- Argon2id stays out of the hot path (login only). Backoff engine unchanged.
- Migration of v1.1/v1.0 installs in §5 of ADR-0031.

## Honest limits

- If the daemon process is compromised, its session key is readable — same
  trust level as D-023/D-045 (self-hosted single-user). Keyring mode unchanged.
- A stolen session password is valid until the daemon next restarts or rotates;
  mitigated by backoff on guessing, `frtrol rotate`/`panic`, and the password's
  ~56.6-bit entropy + Argon2id cost.
