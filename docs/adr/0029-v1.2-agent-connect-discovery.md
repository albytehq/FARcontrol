# ADR-0029 — v1.2.0: Agent connect UX + endpoint resolution (no manual URL)

- Status: ACCEPTED (owner instruction 2026-10-03: master prompt §1, §11–§15,
  §47; ADR scope approved by "lanjut ke ADR dan jalankan mission project 1.2.0")
- Date: 2026-10-03
- Research: docs/research/r7-pairing-ephemeral-credentials.md, r9-error-ux-taxonomy.md,
  r12-localhost-security-ux.md
- Depends on: ADR-0028 (session credentials)

## Context

The agent must connect with **Device ID + Session Password only** (master prompt
§11). It must not be handed a URL, a fingerprint, a token, an IP or a port.
But packets need an address: a bare `FAR-7K2M-QX94` is not routable without a
resolution mechanism. The prompt itself resolves this tension: §14/§15 forbid a
mandatory cloud/relay, and §47 commands technical honesty — no fake
"serverless" that secretly depends on a server.

## Designs considered

1. **Public rendezvous service** (agent queries "where is FAR-XXXX?"). Rejected:
   a mandatory external service violates §14/§15; an optional one still leaks
   device ids + timing metadata to a third party and becomes an availability
   + trust dependency (a compromised rendezvous is a MITM farm).
2. **mDNS/DNS-SD LAN discovery**. Rejected for v1.2: only works on one L2
   segment (not across routers/VPNs/ISPs — §13's actual scenarios), and cannot
   be honestly verified in the sandbox (no second machine). Untestable code in
   a security product is a liability (Rule 2). Revisit only with real hardware.
3. **Address encoded in the pairing secret** (longer code carrying host:port).
   Rejected: §4 fixes the Device ID as short, stable, human-readable; IPs
   change (§13), so the code would rot or leak a topology hint.
4. **Resolution ladder with an explicit, documented fallback** (chosen). Honest,
   fully testable, zero infrastructure.

## Decision

`frtrol agent` (bare) resolves the endpoint in this order:

1. `--url` / `FARCONTROL_URL` — explicit operator override (the documented
   advanced fallback §11 permits).
2. **Remembered host** — the agent home's `connection.json` stores the
   last-good base URL per device id; reconnects reuse it.
3. **Localhost** — `https://127.0.0.1:7788` then `http://127.0.0.1:7788`
   (1 s probe each). Covers the same-machine case and SSH/port-forward setups,
   which is the default deployment for a local-first product.

If none answers: fail closed with a r9-style error ("no FARcontrol answered at
the known addresses — pass --url https://host:7788 once; it is remembered") and
exit 6. TOFU cert pinning (ADR-0025 §4) stays: first connect captures + pins,
`--expect-fp` still available; the pin travels in `connection.json`/agent home.

Interactive prompts (hidden password via termios; never a CLI flag):

- Device ID: `--device`/`FARCONTROL_DEVICE` or prompt (tty).
- Session Password: `--password-file`, `FARCONTROL_SESSION_PASSWORD` (or the
  v1.1 alias `FARCONTROL_PASSWORD`), or hidden tty prompt. Non-tty with no
  source = hard error (scripts use env/file) — an echoed piped password is a
  leak (r7).
- Agent name: `--name` (audit display only), default `agent`.

## Consequences

- Same-machine and tunnel deployments (the tested topology) need exactly
  Device ID + Password — the master prompt's definition of done.
- Cross-network deployments add **one** documented step (env or flag once).
  README states this plainly instead of pretending magic (§47). No relay,
  no cloud, no DHT, no mDNS is built or implied.
- `frtrol agent status/stop` and all capability subcommands read the saved
  `connection.json` — zero re-entry for every later command.
